# 개발 계획 (1단계, 12주)

기준 문서: [game-design-v0.1.md](game-design-v0.1.md)의 본문과 "v0.2 보강 결정" 섹션.
진행 기록: [checklist.md](checklist.md)

## 목표

기획서의 핵심 루프를 **서버 쪽만**, 수치는 임시값으로 구현한다.

```
활동량 입력 → AP → 탐험 준비(지역 확인·스킬·장비) → 탐험 시작(결과 확정) → 시간 경과
→ 결과 수령(S/A/B/C) → 보상(EXP·Gold·재료·아이템) → 상점·제작 → 장비·스킬 변경 → 다음 탐험
```

**1단계 완료 기준:** 미니PC에 배포한 서버에서 Swagger로 위 루프가 한 바퀴 돌아간다.

## 진행 원칙

- **역할:** 엔진·서버의 핵심 코드는 S가 작성한다. Claude는 리뷰, 힌트, 원리 설명을 맡는다.
- **확인 요청 전:** IntelliJ 빌드(`Ctrl+F9`)로 컴파일 오류를 먼저 없앤다. 리뷰는 조용히 틀리는 실수에 집중한다.
- **테스트가 완료 기준:** 각 마일스톤은 JUnit 테스트가 통과하면 완료다. 경계 조건 테스트를 먼저 쓴다.
- **수치는 임시값:** 마일스톤에 들어갈 때 정하고, 나중에 바꾸기 쉽게 한곳(설정)에 모은다. 밸런싱은 12주 범위 밖이다.
- **시간과 랜덤은 바깥에서 넣는다:** 엔진 안에서 `LocalDateTime.now()`나 `new Random()`을 직접 부르지 않는다. 테스트에서 "2시간 뒤", "이 시드" 를 만들 수 있어야 한다. (`java.time.Clock`, 시드를 받는 랜덤 등)

## 구조

```
game-test (저장소)
├─ core/   게임 엔진. 순수 Java. 의존성: JUnit만
└─ app/    Spring Boot 서버. 의존성: Spring + core
```

- 의존 방향은 `app → core` 한쪽뿐이다. `core`에서 Spring을 쓰면 컴파일이 안 된다.
- `core`는 입력을 받아 결과를 돌려준다. 저장(DB)과 HTTP는 `app`의 일이다.
- 지금의 `text-game-app`(아이템 도감 API)은 `app` 쪽 경험으로 이어진다. 구조를 옮길지는 M0에서 정한다.

## 1부. 게임 코어 (core, 순수 Java + JUnit)

### M0. 프로젝트 구조

| 할 일 | 완료 기준 |
|---|---|
| Gradle 멀티 모듈 구성 (`core`, `app`) | `core`에 빈 테스트 하나가 통과 |
| `core`에 JUnit 5만 의존 | `core`에서 `org.springframework` import가 불가능함을 확인 |

**정할 것:** 멀티 모듈로 할지(권장) 별도 프로젝트로 할지. 기존 `text-game-app`을 `app` 모듈로 옮길지, `app`을 새로 만들지.

### M1. 도메인 모델과 최소 콘텐츠

**만들 것**

| 대상 | 내용 |
|---|---|
| 캐릭터 | 레벨, EXP, AP, Gold, 배운 스킬, 장착 스킬(2칸), 무기, 보조, 인벤토리 |
| 아이템 | 종류(재료 / 무기 / 보조), 희귀도(Grade), 장비 효과(별도 데이터) |
| 몬스터 태그 | 3개로 시작 (예: Beast, Undead, Armored) |
| 몬스터 | 이름, 태그, 위협도 |
| 지역 | 난이도, 등장 몬스터, **공개 정보(태그 분포)** 와 **스킬로 여는 정보** |
| 스킬 트리 | 3갈래 × 2단 = 6개, 1단 → 2단 선행 관계 |
| 레시피 | 재료 목록 → 결과 아이템 |
| 상점 목록 | 판매 재료와 가격 |

**최소 콘텐츠 (기획서 27장보다 작게)**

| 대상 | 개수 |
|---|---|
| 지역 | 1 |
| 몬스터 | 3 (태그 하나씩) |
| 스킬 | 6 (3갈래 × 2단) |
| 장비 | 무기 2, 보조 2 |
| 재료 | 2 |
| 레시피 | 1 |

**정할 것:** 스킬 6개의 이름과 효과(대략), 장비 4개의 효과, 레시피 1개. DB 없이 Java 코드로 데이터를 만든다.

**완료 기준:** 콘텐츠를 만들고 조회하는 테스트가 통과.

### M2. AP 경제

**규칙 (v0.2):** AP는 탐험에만 쓴다. 하루 획득 상한, 보유 상한(넘치면 버려짐), 한국 시간 자정 기준, 남은 AP 이월.

| 만들 것 | 테스트할 경계 조건 |
|---|---|
| 하루 활동량(날짜, 걸음 수, 활동 에너지) → AP. **인터페이스**로 분리 (나중에 다른 진행 자원 추가) | 0보, 음수, 비현실적으로 큰 값 |
| 하루 획득 상한 | 상한 직전, 정확히 상한, 상한 + 1 |
| 보유 상한 | 보유량 + 획득량이 보유 상한을 넘을 때 넘친 분이 버려짐 |
| 같은 날짜 중복 정산 거부 | 같은 날짜 두 번 → 두 번째는 AP 변화 없음 |
| 하루 경계 | 23:59:59와 00:00:00 (KST), 서버 시간대가 KST가 아닐 때 |
| AP 차감 | 부족할 때 차감 시도 → 거부, AP가 음수가 되지 않음 |

**정할 임시값:** 걸음 수·활동 에너지 → AP 비율, 하루 획득 상한, 보유 상한.

**설계 질문:** "같은 날짜를 두 번 보냈는데 두 번째 값이 더 크다면?" (워치가 하루 중간에 한 번, 밤에 한 번 보내는 경우) 거부할지, 차이만큼 더할지.

### M3. 탐험 상태 기계

```
대기 ──시작(AP 차감, 결과 확정)──▶ 탐험 중 ──시간 경과──▶ 완료 ──결과 수령──▶ 대기
```

| 규칙 | 테스트 |
|---|---|
| AP가 부족하면 시작 불가 | 정확히 필요한 만큼 있을 때, 1 부족할 때 |
| 탐험 중에 다시 시작 불가 | |
| **탐험 중 장비·스킬 변경 불가** (v0.2) | 탐험 중 장착·해제·스킬 습득·초기화 시도 → 거부 |
| 시간이 덜 지나면 결과 수령 불가 | 종료 시각 1초 전, 정각, 1초 후 |
| 같은 결과 두 번 수령 불가 | 중복 수령 방지 |
| 결과는 시작 시점에 확정 (v0.2) | M3에서는 판정을 가짜(고정 결과)로 넣고, M4에서 진짜 판정으로 교체 |

**정할 임시값:** 탐험 1회 AP 비용, 탐험 시간.

**설계 질문:** "완료"를 저장된 상태로 둘 것인가, `지금 시각 ≥ 종료 시각`으로 그때그때 계산할 것인가. 시간이 흐르는 것만으로 상태가 바뀌는 경우를 어떻게 표현할지가 이 마일스톤의 핵심 질문이다.

### M4. 탐험 적합도 판정 (게임의 심장)

```
기본 점수 (캐릭터 레벨 vs 지역 난이도)
+ 태그 대응 (장착 스킬·장비가 지역의 등장 태그와 맞는 정도)
= 적합도
+ 작은 랜덤 (바깥에서 넣음)
→ 구간에 따라 S / A / B / C
```

| 테스트할 것 |
|---|
| 같은 준비 + 같은 랜덤 시드 → 항상 같은 결과 |
| 태그가 맞는 스킬·장비를 장착하면 적합도가 오름 |
| 구간 경계값: S 기준 바로 아래 / 정확히 / 바로 위 |
| 랜덤이 결과를 몇 단계까지 바꿀 수 있는가 (기획서: 랜덤은 "약간의 변화") |
| 판정 입력은 시작 시점의 스냅샷. 시작 후 바뀐 값은 결과에 영향 없음 |

**정할 임시값:** 기본 점수 계산식, 태그 대응 보너스, 랜덤 폭, S/A/B/C 구간.

**설계 질문:** 지역의 태그 분포(예: Beast 60%, Undead 30%, Armored 10%)를 적합도에 어떻게 반영할지. 가중 평균인가, 가장 많은 태그만 보는가.

### M5. 보상과 성장

| 만들 것 | 테스트할 경계 조건 |
|---|---|
| 등급 → EXP, Gold, 재료 | **C도 최소 보상** (v0.2: 실패 없음) |
| 아이템 드롭: 희귀도(Grade)별 확률, 탐험 등급이 높을수록 높은 희귀도 가능 | 랜덤 시드 고정으로 드롭 결과 검증 |
| 레벨 업 | 한 번에 두 레벨 이상 오를 때, 넘친 EXP 이월 |
| 최고 레벨 20 | 19에서 대량 EXP → 20에서 멈춤, 20에서 EXP 획득 → 쌓이지 않음 |
| 스킬 습득 기회 | 레벨 3, 6, 9, 12, 15, 18 도달 시 1회씩. 한 번에 여러 레벨이 올라 두 기회를 지날 때 |

**정할 임시값:** 등급별 보상표, 희귀도별 드롭 확률, 레벨별 필요 EXP.

**설계 질문:** 습득 기회를 쓰지 않고 다음 기회 레벨에 도달하면, 기회가 쌓이는가.

### M6. 상점과 제작

| 만들 것 | 테스트할 경계 조건 |
|---|---|
| 상점: Gold로 재료 구매. 가격은 희귀도에 따라 | Gold 부족, 정확히 가격만큼 있을 때, 수량 0·음수 구매 |
| 제작: 레시피의 재료만 소비 → 아이템 생성 (v0.2) | **재료가 일부만 있을 때 아무것도 소비하지 않고 거부** (원자성) |
| 인벤토리 수량 | 0 아래로 내려가지 않음 |

**정할 임시값:** 재료 가격, 판매하지 않는 희귀도.

### M7. 빌드: 스킬 트리와 장비

| 만들 것 | 테스트할 경계 조건 |
|---|---|
| 스킬 습득: 습득 기회 1회 소비 | 기회가 없을 때, 2단을 1단 없이 배우려 할 때, 이미 배운 스킬 |
| 스킬 장착 2칸 | 배우지 않은 스킬, 3번째 장착, 같은 스킬 두 칸 |
| 스킬 초기화: Gold 소비, 배운 스킬을 습득 기회로 되돌림 | Gold 부족, 장착 중인 스킬 처리 |
| 장비 장착: 무기 칸 / 보조 칸 | 무기를 보조 칸에, 인벤토리에 없는 장비 |
| 탐험 중 잠금 (M3 규칙) | 위 모든 변경이 탐험 중이면 거부 |
| 장착 결과가 M4 적합도에 반영 | |

**정할 임시값:** 초기화 비용.

### M8. 게임 코어 통합 테스트 (1부 완료 기준)

JUnit 테스트 하나로 한 바퀴:

> 활동량 입력 → AP → 탐험 시작 → 시간 경과 → 결과 수령(낮은 등급) → 재료·Gold 획득 → 상점에서 부족한 재료 구매 → 제작 → 장비 장착 + 스킬 습득·장착 → 같은 지역 재탐험 → **적합도가 올라 더 높은 등급**

"빌드를 바꾸면 결과가 달라진다"를 코드로 증명하면 1부가 끝난다.

| 지역 목록·공개 정보 | M1 | |

**사용자 식별:** 12주 동안은 캐릭터 ID를 요청에 직접 넣는다. 로그인은 3단계에서 한다.
