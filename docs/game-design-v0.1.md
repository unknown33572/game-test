# Apple Watch 활동량 기반 방치형 RPG — 게임 기획 기준서 v0.1

## 1. 게임 한 줄 정의

Apple Watch의 일상 활동량과 걸음 수를 게임 자원으로 전환하고, 그 자원을 탐험·제작·스킬·장비에 투자하여 하나의 캐릭터를 성장시키는 Apple Watch 중심 방치형 RPG.

핵심은 직접 전투가 아니라,

> 현실에서 움직인다 → 게임 자원을 얻는다 → 무엇에 투자할지 결정한다 → 탐험한다 → 결과와 보상을 확인한다 → 캐릭터와 빌드를 바꾼다 → 다시 탐험한다

라는 짧은 의사결정 루프다.

## 2. 게임의 핵심 철학

### 2.1 Apple Watch의 제약을 게임의 특징으로 사용

Apple Watch는 화면이 작고 입력 방식이 제한적이므로 스마트폰 RPG처럼 직접 전투를 조작하는 구조를 사용하지 않는다.

플레이어의 핵심 행동은 다음과 같다.

- 확인
- 선택
- 탐험
- 결과 확인
- 장비/스킬 변경
- 제작
- 다음 행동 결정

즉, "전투를 직접 플레이하는 게임"이 아니라 "전투와 탐험의 결과를 준비하고 결정하는 게임"을 목표로 한다.

## 3. 핵심 재미

게임의 재미는 직접적인 액션보다 다음과 같은 선택과 결과에서 발생한다.

- 어디로 갈 것인가?
- 어떤 지역을 선택할 것인가?
- 어떤 스킬을 장착할 것인가?
- 어떤 장비를 사용할 것인가?
- AP를 어디에 사용할 것인가?
- 어떤 재료를 모을 것인가?
- 무엇을 제작할 것인가?
- 탐험 결과가 어떻게 나올 것인가?
- 어떤 아이템을 얻을 것인가?
- 다음 탐험에서는 빌드를 바꿀 것인가?

따라서 플레이어가 느껴야 하는 핵심 순환은 다음과 같다.

```
활동
 ↓
자원 획득
 ↓
선택
 ↓
탐험/제작
 ↓
결과
 ↓
보상
 ↓
성장
 ↓
빌드 변화
 ↓
새로운 선택
```

## 4. 핵심 게임 루프

### 4.1 기본 루프

```
현실 활동
 ↓
Steps / Active Energy
 ↓
Activity Point(AP)
 ↓
플레이어의 행동 선택
 ↓
탐험 / 제작 / 성장 관련 행동
 ↓
결과 획득
 ↓
EXP / Gold / Material / Item
 ↓
캐릭터 성장
 ↓
스킬 / 장비 / 빌드 변화
 ↓
다음 탐험
```

### 4.2 현실 위치 기반 지역 해금

현실에서 실제 장소를 방문하면 해당 게임 지역이 해금된다.

```
실제 장소 방문
 ↓
GPS 위치 판정
 ↓
게임 지역 영구 해금
 ↓
해당 지역의 몬스터 / 재료 / 아이템 / 레시피 / 콘텐츠 접근
```

중요한 원칙: 한 번 실제 장소에 도착하여 해금하면 이후 계속 그 장소에 있을 필요는 없다. 즉 GPS는 실시간 이동 플레이가 아니라 게임 월드 확장 장치다.

## 5. Apple Watch / HealthKit

### 확정

Apple Watch의 활동 데이터를 게임 자원으로 사용한다.

현재 사용하기로 한 핵심 데이터:

- Step Count
- Active Energy

HealthKit에서 얻은 활동량을 기반으로 게임 내 AP를 계산한다.

### 아직 미정

정확한 AP 환산 공식은 아직 확정하지 않는다.

```
Steps
+
Active Energy
 ↓
AP
```

구체적인 비율과 하루 최대 획득량은 별도 밸런싱 단계에서 결정한다.

## 6. 게임 자원 구조

현재 기본적으로 다음 자원을 사용한다.

### AP — Activity Point

게임에서 가장 중요한 행동 자원. 개념적으로 "무엇을 할 것인가?"를 결정하는 자원.

사용 대상 예:

- 탐험
- 제작
- 스킬/빌드 관련 행동
- 기타 성장 행동

MVP에서는 Skill Point, Craft Point 등 여러 행동 포인트를 별도로 만들지 않고 AP 하나로 통합한다.

### Stamina / Action Capacity

하루에 수행할 수 있는 의미 있는 행동량을 제한하는 별도의 개념. 개념적으로 "오늘 몇 번 행동할 수 있는가?"

AP와 역할을 분리한다.

```
AP
= 행동에 사용하는 자원

Stamina
= 행동 횟수/실행 가능량 제한
```

정확한 이름은 추후 확정할 수 있으나, HP라는 이름을 일일 행동량으로 사용하는 것은 지양한다.

### EXP

캐릭터 성장에 사용되는 경험치. 단순히 걷는 양 자체를 EXP로 바꾸지 않는다.

기본 개념: 유효한 게임 행동을 완료한 결과로 EXP를 얻는다.

- 탐험 완료
- 제작 완료
- 기타 유효 행동

정확한 EXP 획득량은 미정.

### Gold

게임 내 화폐.

주요 획득 경로:

- 탐험
- 아이템 판매 등

사용처:

- 상점
- 제작
- 장비/성장 관련 시스템 등

세부 경제 구조는 추후 결정.

### Material

제작에 사용하는 재료.

주요 획득 경로:

- 탐험
- 상점

원칙적으로 탐험이 핵심 재료 공급원이 되도록 설계한다.

### Item

탐험이나 제작으로 얻는 게임 자산.

- 장비
- 기타 수집 아이템

장비는 단순한 공격력 증가보다 탐험 적합성이나 빌드 선택을 변화시키는 방향을 우선한다.

## 7. 캐릭터

### 기본 구조

플레이어당 캐릭터는 1명으로 시작한다.

```
Character
├─ Level
├─ EXP
├─ Stamina / Action Capacity
├─ Class
├─ Skill Set
├─ Equipment
├─ Gold
└─ Title / 기타 성장 요소
```

## 8. 클래스

### MVP 확정

Warrior(전사) 1개 클래스만 사용한다. 현재는 다중 클래스 시스템을 만들지 않는다.

이유:

- MVP 복잡도 감소
- 핵심 루프 검증 우선
- 스킬/장비/탐험 시스템 자체의 재미 검증 가능
- 클래스 밸런스 작업을 뒤로 미룰 수 있음

추후 게임성이 검증되면 다른 클래스를 추가할 수 있다.

## 9. 전투 시스템 기본 방향

### 핵심 원칙

플레이어가 전투를 직접 조작하지 않는다. Apple Watch의 입력 한계를 고려하여 자동 판정 방식으로 처리한다.

전투는 별도의 대형 RPG 전투 엔진이 아니라 탐험 결과를 결정하는 판정 엔진에 가깝다.

### MVP에서 제외

다음 시스템은 만들지 않는다.

- 공격력 스탯
- 방어력 스탯
- 몬스터 HP
- 데미지 공식
- 턴 전투
- 실시간 스킬 사용
- 쿨다운 시스템
- 복잡한 상태이상
- 실시간 전투 조작

## 10. 탐험 판정 시스템

현재 가장 중요한 전투/탐험 핵심 시스템.

```
지역
+
등장 몬스터
+
몬스터 태그
+
캐릭터 레벨
+
장착 스킬
+
장비
 ↓
탐험 적합도(Compatibility Score)
 ↓
랜덤 요소
 ↓
탐험 결과 등급
 ↓
보상
```

내부적으로 계산 점수를 사용하되, 사용자에게는 탐험 적합도와 같은 개념으로 표현한다. 이 값은 공격력의 대체물이 아니라 "현재 준비 상태가 해당 탐험에 얼마나 적합한가"를 의미한다.

## 11. 탐험 결과

예정된 기본 결과 등급:

- S
- A
- B
- C

등급에 따라 보상량과 보상 품질이 달라질 수 있다.

랜덤 요소는 존재할 수 있지만, 플레이어의 준비와 선택이 결과의 핵심이고 랜덤은 결과에 약간의 변화를 주는 정도로 제한한다.

## 12. 몬스터

몬스터는 단순한 HP/공격력 집합으로 만들지 않는다.

### 기본 구조

```
Monster
├─ monsterId
├─ name
├─ tags
├─ threat
└─ lootTable
```

### 몬스터 태그 예시

테스트용 후보:

- Beast
- Undead
- Demon
- Plant
- Flying
- Armored
- Aquatic
- Poison 등

태그는 스킬/장비/지역과 상호작용하는 핵심 데이터가 된다.

## 13. 지역

지역은 현실의 실제 장소와 연결된다.

### 기본 구조

```
Region
├─ regionId
├─ displayName
├─ latitude
├─ longitude
├─ unlockRadius
├─ difficulty
└─ lootTable
```

지역은 다음 요소와 연결된다.

- 등장 몬스터
- 몬스터 태그
- 재료
- 아이템
- 레시피
- 난이도
- 기타 지역 특성

## 14. 지역 명명 방향

실제 한국 지명을 그대로 쓰는 것이 아니라 게임적인 이름으로 변형한다.

```
인천
→ 마계인천
→ Incheon Inferno

용산
→ Dragon Mountain

쌍문
→ Twin Gates
```

원칙:

- 실제 위치를 알아볼 수 있음
- 판타지 요소를 부여
- 지역별 몬스터/재료/스토리/기믹과 연결 가능

## 15. 스킬 시스템

스킬은 단순 공격력 증가보다는 탐험 선택을 바꾸는 기능을 갖는 방향으로 설계한다.

### 테스트용 예시

```
Beast Hunter
→ Beast 적합도 증가

Undead Bane
→ Undead 적합도 증가

Armor Breaker
→ Armored 적합도 증가

Scout
→ 탐험 정보/특수 탐색 보너스

Tracker
→ 특정 몬스터 관련 정보/출현 보너스

Forager
→ 재료 획득량 증가

Endurance
→ 행동 효율 관련 보너스
```

위 스킬은 예시이며 최종 확정 콘텐츠가 아니다.

## 16. 스킬의 역할

스킬은 다음과 같은 빌드를 만들어내는 방향이다.

```
전투 특화
탐험 특화
재료 수집 특화
효율 특화
특정 지역/몬스터 특화
```

따라서 같은 Warrior라도 스킬 조합에 따라 다른 플레이 스타일을 만들 수 있어야 한다.

## 17. 장비

장비 역시 단순 스탯 증가 방식보다는 탐험 적합성/행동 효율/보상 특성을 변화시키는 방향을 우선한다.

```
화염검
→ 특정 몬스터/태그 대응

사냥꾼의 망토
→ Beast 계열 대응

탐험화
→ 탐험 효율 증가

채집 장갑
→ Material 획득 증가
```

이 역시 테스트 예시이며 세부 장비 시스템은 미정이다.

## 18. 제작

제작은 방치형으로 처리하지 않고 플레이어가 직접 조합하는 행동으로 한다.

```
Material
+
Material
 ↓
Recipe
 ↓
Item
```

예:

```
Iron Scrap ×3
Leather ×2
 ↓
Hunter Sword
```

### MVP 방향

가능한 한 단순하게 한다.

- 즉시 제작
- 제작 실패 없음
- 재료 소비
- 명확한 결과
- 레시피 기반

제작에 AP를 사용할지, Gold를 사용할지, 제작 시간 등을 어떻게 둘지는 추후 결정.

## 19. 활동 / 탐험 / 제작의 관계

세 시스템은 서로 독립된 메뉴가 아니라 연결된 성장축이어야 한다.

```
활동
 ↓
AP
 ↓
탐험
 ↓
재료 / 아이템 / Gold
 ↓
제작
 ↓
장비
 ↓
탐험 적합성 변화
 ↓
새로운 지역/탐험 도전
```

스킬 역시 이 구조 안에서 작동한다.

```
활동
 ↓
AP
 ↓
탐험
 ↓
성장
 ↘ 스킬
 ↘ 장비
 ↘ 제작
      ↓
   새로운 탐험 선택
```

## 20. 방치 진행

방치 요소는 존재하지만 단순한 "탐험 보내기 → 기다리기 → 보상 받기"만으로 끝내지 않는 것을 원칙으로 한다.

탐험 전에는 반드시 의미 있는 선택이 존재해야 한다.

```
어디를 갈지
+
어떤 스킬을 사용할지
+
어떤 장비를 사용할지
+
현재 자원을 어디에 투자할지
```

그 결과를 나중에 확인하는 구조가 핵심이다.

## 21. 시간 기반 진행

탐험은 자동으로 진행될 수 있다.

```
탐험 시작
 ↓
서버에서 진행 상태 관리
 ↓
시간 경과
 ↓
탐험 완료
 ↓
결과 확인
```

정확한 탐험 시간과 시간 경과 규칙은 아직 확정하지 않는다.

## 22. 서버 구조

### 서버의 역할

Spring Boot 서버를 게임의 원장(Source of Truth)으로 사용한다. Apple Watch는 활동 데이터를 읽고 게임에 필요한 데이터를 전달하며, 게임 상태는 서버가 관리한다.

```
Apple Watch
 ├─ HealthKit
 └─ Game UI
       ↓
     Spring Server
       ↓
       DB
```

### 서버가 관리할 핵심 데이터

- 캐릭터 상태
- AP
- Stamina
- EXP
- Gold
- Materials
- Items
- Skills
- Equipment
- Regions
- Exploration state
- Exploration result
- Guild
- Guild War
- 기타 게임 기록

## 23. 길드

길드는 존재시키되 가볍게 만든다.

```
Guild
├─ guildId
├─ name
├─ leader
├─ members
└─ score
```

대규모 MMORPG형 소셜 시스템은 목표가 아니다.

## 24. 길드전

### 기본 방향

실시간 PvP가 아니다. 서버가 정해진 시점에 캐릭터 상태를 기준으로 결과를 계산하는 비동기 전투다. 탐험 판정 시스템과 동일한 엔진을 재사용한다.

```
Guild A
VS
Guild B
 ↓
각 멤버의 빌드/적합도 비교
 ↓
전투 결과 계산
 ↓
길드 승패 결정
```

MVP에서는 복잡한 별도 전투 엔진을 만들지 않는다.

## 25. 길드전의 역할

길드전은 메인 게임이 아니라 개인이 만든 캐릭터 빌드를 사회적으로 검증하는 콘텐츠에 가깝다.

```
개인 성장
 ↓
빌드 구성
 ↓
탐험
 ↓
강한 빌드 발견
 ↓
길드전
 ↓
빌드 비교
```

## 28. 게임의 핵심 차별화 방향

게임 자체의 개별 요소가 전부 완전히 새로운 것은 아니다. 하지만 다음 조합을 하나의 경험으로 만드는 것을 목표로 한다.

```
Apple Watch
+
HealthKit 활동량
+
AP 경제
+
현실 위치 기반 지역 해금
+
자동 탐험
+
빌드 선택
+
제작
+
1캐릭터 성장
+
비동기 길드전
```

특히 핵심 아이디어는: 현실의 움직임이 게임 세계를 확장하고, 활동량이 게임에서 사용할 선택 자원이 된다.

그리고 플레이어는 전투를 직접 조작하는 대신 캐릭터의 준비 상태와 탐험 선택을 설계한다.

## 29. 현재 확정된 설계 원칙

다음은 이후 세부 설계에서도 유지해야 하는 기준이다.

1. Apple Watch에서 가능한 인터랙션 수준을 넘지 않는다.
2. 직접 전투보다 선택과 결과 확인을 중심으로 한다.
3. 복잡한 RPG 전투 엔진을 만들지 않는다.
4. AP를 중심으로 여러 행동 자원을 통합한다.
5. 탐험/스킬/장비/제작이 서로 연결되어야 한다.
6. 현실 활동과 게임 플레이가 연결되어야 한다.
7. 현실 위치는 게임 콘텐츠 해금 수단으로 사용한다.
8. MVP에서는 콘텐츠보다 핵심 루프 검증이 우선이다.
9. 서버가 게임 상태의 원장 역할을 한다.

## 부록: 12주 계획과의 연결 (2026-10-08 결정)

이 기획서는 장기 방향이다. 12주(1단계) 동안의 범위는 아래로 한정한다.

| 항목 | 결정 |
|---|---|
| 전투 판정 | 인수인계서의 "텍스트 턴제 전투"를 이 문서 10장의 **탐험 적합도 판정**으로 교체 |
| Apple Watch·HealthKit | 인수인계서대로 **3단계**로 미룸. 12주 동안 Swift·워치 개발 없음 |
| 활동량 입력 | 서버가 **API로 활동량을 받는 것까지**. 12주 동안은 Swagger·Postman이 워치 역할 |
| 수치·공식 (30장) | 엔진은 임시값으로 만들고 설정으로 분리. 밸런싱은 12주 범위 밖 |

### 3단계 이식을 위해 12주 동안 지킬 것

- 활동량은 **하루 단위**로 받는다 (날짜, 걸음 수, 활동 에너지)
- 같은 날짜를 두 번 보내도 AP가 두 번 들어가지 않는다 (멱등성)
- "하루"의 기준(자정, 시간대)은 서버가 정한다
- 걸음 수·위치는 클라이언트만 아는 값이므로 서버는 하루 상한, 중복 정산 방지, 비현실적인 값 거부로 방어한다

### 3단계에서 새로 생기는 일 (참고)

- 워치 앱: Swift·SwiftUI, HealthKit 권한·읽기, 백그라운드 동기화, 위치 권한, 오프라인 처리, 앱 심사
- 서버 추가: 사용자 로그인과 토큰 검증, 탐험 완료 푸시 알림, 외부 공개 주소와 HTTPS
